# The info file

Write a show's `.txt`: who, when, where, and the setlist with a time on every track, built
from the tags `lh tag` already wrote.

Every seed carries one, and it is the last thing a trader still types by hand once a set is
named, tagged and checksummed. The facts are all in the files already — titles in `TITLE`,
lengths in STREAMINFO — so a tool that tags a show can write its setlist for free.

---

## 0. The standard, and where it comes from

From the etree wiki's [SeedingGuidelines](https://wiki.etree.org/index.php?page=SeedingGuidelines),
quoted rather than remembered, as in `docs/tagging.md` §0:

* **Contents.** "Include the band name, date and venue." "Include source information that is
  as complete as possible: full genealogy…" "Include a track listing with disc and track
  numbering, song titles, and ideally track timings as well." "Add track and disc timings to
  help people decide what length disc to use (74 vs 80 min)." "Add any observations and
  notes. Point out flaws or splices."
* **Format.** "save as plain text, not a fancier format like .doc".
* **Name.** "Name the .txt file according to our NamingStandards and place it in the same
  directory" — so `hurula2026-08-08.txt`, the `bbyyyy-mm-dd` stem, not the whole folder name.
* The wiki points at a "track length program" that "will pull the timing info right from an
  audio disc copy and make a starter text file". This feature is that program, reading FLACs
  instead of a disc.

The wiki's example info files live on db.etree.org, which now sits behind a bot check; the
layout below follows the wiki's rules and common practice rather than a copied example.

---

## 1. Decisions taken up front

* **A starter file, not a finished one.** What the tags cannot say — lineage beyond
  `COMMENT`, set breaks, encores, flaws — is left for the trader to add by hand afterwards.
* **Never overwrite by default.** An existing info file is usually hand-written and cannot be
  regenerated, so writing over one takes `--force`. Editing only the setlist block inside an
  existing file would mean parsing free-form prose, which `docs/tagging.md` §2 already ruled
  out. Principle 1 holds unamended: this only ever creates a file.
* **Preview is the default; `--yes` writes**, the same as `tag` and `rename`.
* **UTF-8 without a BOM, CRLF line endings.** The audience is mostly on Windows; CRLF reads
  everywhere, LF still does not in every tool traders use.
* **FLAC only**, for the same reason as tagging (`docs/tagging.md` §4): a non-FLAC file has no
  `TITLE` and is not a track. It is reported, never silently left out (Principle 5).

## 2. The layout

```
Hurula
2026-08-08
Live at Malmöfestivalen 2026-08-08
<LOCATION, when set>

Source: <COMMENT, or left blank to fill in>

Disc 1 [63:41]
d1t01  Ett annat språk   4:12
d1t02  …                 3:58

Total: 63:41

Generated by Lossless Little Helper 0.1.0
```

* The header is `ARTIST`, `DATE`, `ALBUM`, `LOCATION` — a line each, a missing one left out.
* A track is labelled from its etree file name (`d1t01`, or `t01` for a set with no discs);
  a file whose name is not an etree name falls back to its position.
* `Disc N [m:ss]` headers only appear when the file names carry discs.
* Times are `m:ss`, rounded. Disc and show totals are summed from frame counts and rounded
  once, so they never drift from adding up already-rounded track times.
* Titles are padded so the times line up, counting characters, not display width.

---

## 3. What gets said instead of silently fixed

`InfoPlan::problems`, printed before the preview and shown in the TUI:

* a FLAC with no `TITLE` — rendered as `(no title)`;
* a show-level field (`ARTIST`, `DATE`, `ALBUM`, `LOCATION`, `COMMENT`) that differs between
  files — the first file's value is used;
* a file whose length its header does not state;
* a CD-audio disc longer than 80:00, which will not fit on a CD-R;
* a non-FLAC file, left out;
* another `.txt` already in the folder — probably an info file under a different name.
